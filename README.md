В исходном запросе допущены 4 критические ошибки оптимизации:
1) Декартово произведение с таблицей film:
В блоке FROM перечислена таблица film f.Однако в блоке WHERE полностью отсутствует условие связи таблицы фильмов со складом (нет i.film_id = f.film_id).
Последствие: База данных перемножает каждую найденную строку со всеми 1000 фильмами каталога. Если найдено 600 строк платежей, в памяти генерируется массив строк.
2) Нарушение принципа SARGable: вызов функции DATE(p.payment_date):
Когда колонка оборачивается в функцию DATE(...), СУБД отключает возможность поиска по B-Tree индексу.Последствие: Сервер вынужден выполнять Full Table Scan — сканировать каждую запись таблицы payment, на лету преобразовывать дату и только потом сравнивать со строкой '2005-07-30'.
3) Некорректное соединение по датам: p.payment_date = r.rental_date:Таблицы payment и rental логически связываются через первичный ключ rental_id.Сравнение по временным меткам заставляет базу тратить ресурсы на сопоставление неиндексированных дробных дат вместо мгновенного перехода по ключу.
4) Избыточная связка SUM() OVER (...) + DISTINCT:Оконная функция с PARTITION BY вычисляет сумму отдельно для каждой из сотен тысяч размноженных строк.После этого оператор DISTINCT создаёт временную таблицу (часто сбрасываемую на диск) и запускает тяжёлую сортировку для удаления одинаковых дубликатов. Здесь естественнее и быстрее работает классический GROUP BY.
